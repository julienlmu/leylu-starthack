# pr263-fix: lookalike check never declines a real customer after an impostor; fewer false red flags
- Who: Julien (tool: Claude Code)
- Branch: julien/pr263-fix (on top of #263 orhun/lookalike, origin/main merged)
- What changed:
  - A declined session (outcome lost, no request read: lookalike or credential decline) no longer makes its sender a known customer. Before, an impostor's own declined session let its second mail through (quoted), and a real customer writing for the first time after an impostor would be declined as the impostor's lookalike.
  - Red flags no longer match ordinary RFQ wording: "send us your quote" and "delivery to our new address" (only "new e-mail (address)", confirm/resend/forward your price).
  - Cyrillic look-alike letters (е, о, а ...) count as Latin (hofmann-tеxtilwerk@ was only "weak"); the same long local part at another provider (hofmann-textilwerk@gmail.com) is a weak lookalike (red flag needed).
  - Tests: 16 real @hackloop.mail senders never match each other; hofmann-textilwerk lookalikes vs a colleague / a new company (hofmann-logistik@) / display-name spoof.
- Files touched: agent/lookalike.py, agent/main.py, agent/test_lookalike.py, agent/AGENTS.md
- Contract/API changes: none
- New env vars / packages: none
- How verified: make check (agent 2636 passed; test_next_traps_15b rate-desk test is flaky on origin/main too, 1 of 4 runs), test_lookalike.py 39 passed
- Known issues / TODO: a lookalike quoted before the real customer ever wrote still makes the real customer's first RFQ look like its lookalike (5U's trap order makes this unlikely). Display-name spoofing from an unrelated domain is not caught (could be a real new contact).
